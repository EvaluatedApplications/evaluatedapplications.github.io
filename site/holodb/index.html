We keep the answers, not just the rows

how it works

Most databases answer SELECT SUM(amount) by reading every row and adding it up. Ten times the rows, ten times the wait.

HoloDb keeps a running answer instead. Each column's total lives in a small maintained accumulator — a tally that updates as rows go in and out, using a holographic encoding that packs a running sum into a fixed-size vector you can read back in constant time.

So when you ask for the total, HoloDb doesn't count — it reads the tally it's been keeping. That's why the answer stays a fraction of a microsecond whether the table holds one million rows or twenty-five million. The same idea powers COUNT, GROUP BY, MIN/MAX and DISTINCT: the work happened once, at write time, so every read is nearly free.

Integer SUM/COUNT are exact and constant-time (a residue-phase codec). Real-number sums fall back to a fast SIMD pass — still quick, but we'll always tell you which.

the honest scoreboard

The same queries over the same rows on DuckDB, SQL Server and HoloDb, each loaded through its own bulk path, every result checked byte-for-byte identical across all engines before timing (median of many runs, 16 cores). SQL Server is a real, durable, on-disk peer — SQL Server 2022 in Docker, a persistent database on a volume, buffer pool capped at 1 GB — so at 25M rows its data outgrows the cache and it reads from disk. DuckDB is a superb columnar engine and the fastest loader here — if grouped real-number rollups and raw load throughput are your whole workload, use it. HoloDb's bet is the mixed transactional + analytics + vector workload, where maintained aggregates and durability change the shape of the problem.

SQL Server is durable and on-disk here (persistent DB, 1 GB cache) and pays a network round-trip; HoloDb can also be durable and larger-than-memory (its paged engine spills to disk) and still answer these aggregates in microseconds. capabilities

Transactional SQL

Real ACID: a reader/writer lock, pre-transaction snapshot rolled back on any error, fsync write-ahead log, and crash recovery bounded by live data, not write history. A substantial SQL dialect — joins, subqueries in IN, LIKE, BETWEEN, GROUP BY/HAVING, transactions.

One PRIMARY KEY per table (INT or TEXT). No OUTER joins or ALTER TABLE yet.

Size-independent analytics

Whole-table COUNT/SUM/MIN/MAX and single-column GROUP BY answer from maintained holographic accumulators and per-block zone maps — O(1), no scan, flat as the table grows. Compiled predicates and a columnar path keep ordinary filters fast too.

Integer aggregates are exact + constant-time; real-number sums use a SIMD scan.

Vector search (NEAREST)

Holographic similarity search in SQL: SELECT … FROM t NEAREST (col=val,…) LIMIT k ranks rows by similarity to a partial key — a vector-DB query over the same rows, with no separate vector index to build or keep in sync. Sublinear LSH index above ~8,000 rows.

In-RAM engine has the LSH index; NEAREST can't yet combine with WHERE/GROUP.

Durable, larger-than-memory

The paged engine stores tables on an 8 KB buffer-pool page store with a redo-only WAL: cold pages spill to disk, so a table can exceed RAM, with bounded crash recovery — and the size-independent aggregates are maintained on disk.

The primary-key index stays in RAM (~16 B/row) — the limit for tables far bigger than memory.

Live metrics under ingest

Whole-table and grouped counts/sums are served from an immutable snapshot republished after every write — without taking the engine lock — so a continuous streaming ingest never stalls a dashboard read.

Metered billing spine

Every query reports the bytes it actually read versus the bytes a scan-priced warehouse would bill — the exact metric BigQuery and Athena charge on. Constant-time aggregates read ~0 bytes yet bill as a scan, so you can run a metered analytics API that undercuts the warehouse.

deploy

Embedded, in-process

var db = new HoloDbService(new HoloDbOptions { WalPath = "app.wal" }); db.Execute("CREATE TABLE t (id INT PRIMARY KEY, region TEXT, amount REAL)"); var r = await db.ExecuteAsync("SELECT region, SUM(amount) FROM t GROUP BY region");

Sync or async, plus a column-native BulkLoad. Register with DI via AddHoloDb(), or attach to an EvalApp pipeline.

Networked server + typed client

docker run -p 5432:5432 -v holodb-data:/data \ ghcr.io/evaluatedapplications/holodb:latest --token s3cret

A self-hosted TLS server; the .NET client mirrors the embedded surface, so you go from in-process to networked by changing only how you get the handle. Columnar results stay columnar on the wire.

In the browser (WebAssembly)

The in-memory engine is pure managed .NET, so it compiles to WebAssembly and runs client-side — the Analyst tool is a real HoloDb in a browser tab, nothing leaving the device. Ideal for local/offline analytics and "your data stays with you" apps.

The Docker image is rebuilt from source and published as :latest (and :<version>) on every release, so :latest is always the current engine.
