Benchmarks — the full method and every number

The same SQL over the same data, on HoloDb (embedded), HoloDb (networked server), DuckDB, and a durable on-disk SQL Server. Every result is verified byte-for-byte identical across all engines before it's timed, so the comparison is honest — including the queries HoloDb loses.

How it's run

  • Same data, same SQL. Six columns (int keys, an int measure, a text grade, a real amount), generated once with a fixed seed and loaded into every engine through its own idiomatic bulk path.
  • Verified identical. Before timing, each query's full result set is normalized and compared across all engines — if any engine disagrees, the run is flagged, not published. Every number below passed.
  • Timed fairly. Median of many runs of execute + consume-all-rows through each engine's own typed client API (no boxing), on a 16-core machine.
  • DuckDB runs in-process, in memory (its fastest mode).
  • SQL Server is the durable, on-disk peer: SQL Server 2022 in Docker, a persistent user database on a volume, buffer pool capped at 1 GB. At 25M rows the table outgrows that cache, so its reads come off disk — a fair "durable service" comparison. It also pays a client/server round-trip the embedded engines don't.
  • HoloDb runs both embedded (in-process) and as a networked TLS server (the fair peer to SQL Server's round-trip).
  • Honest boundary. Integer SUM/COUNT are exact and constant-time; real-number sums use a SIMD scan (which is why grouped real-sums lose to DuckDB).

What the numbers say

HoloDb's maintained aggregates (SUM, COUNT, GROUP BY, MIN/MAX, DISTINCT) answer in microseconds and don't grow with the table — the numbers barely move from 10M to 25M, while SQL Server's climb and its disk-bound scans reach seconds. HoloDb also wins the ordinary filter scans. It loses grouped real-number rollups, ORDER BY+LIMIT, filtered COUNT, and raw bulk load to DuckDB — shown above, not hidden. DuckDB is an excellent pure-columnar engine; HoloDb's edge is the mixed transactional + analytics + vector workload, durable and larger-than-memory, in one embeddable dependency.
