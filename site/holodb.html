Benchmarks — the full method and every number

One realistic workload — a billing SaaS's invoice ledger — run as two apples-to-apples comparisons we keep separate: the in-process, in-memory engines against each other (HoloDb embedded vs DuckDB), and the networked services against each other (HoloDb server vs a durable on-disk SQL Server). Every result is verified byte-for-byte identical across all four engines before it's timed, so the comparison is honest — including the queries HoloDb loses.

The workload

CREATE TABLE invoices ( invoice_id INT PRIMARY KEY, -- 25,000,000 invoices customer_id INT, -- ~500,000 customers, ~50 invoices each month INT, -- yyyymm, 202301 … 202412 (24 months) region TEXT, -- US 40% / EU 30% / APAC 20% / LATAM 10% status TEXT, -- paid 78 / pending 10 / overdue 7 / refunded 3 / failed 2 (%) amount_cents INT -- money as integer minor units (cents), long-tail $20–$50,000 );

How it's run

  • Same data, same SQL. The invoices table above, generated once with a fixed seed and loaded into every engine through its own idiomatic bulk path.
  • Real billing queries. The eleven queries are the ones a subscription business actually runs: revenue by status / month / region, the running total and invoice count, a single-invoice lookup, overdue outstanding, big-ticket count, largest invoices, top customers, and a region×status breakdown.
  • Verified identical. Before timing, each query's full result set is normalized and compared across all engines — if any engine disagrees, the run is flagged, not published. Every number below passed.
  • Timed fairly. Median of many runs of execute + consume-all-rows through each engine's own typed client API (no boxing), on a 16-core machine.
  • DuckDB runs in-process, in memory (its fastest mode).
  • SQL Server is the durable, on-disk peer: SQL Server 2022 in Docker, a persistent user database on a volume, buffer pool capped at 1 GB. At 25M invoices the table outgrows that cache, so its reads come off disk — a fair "durable service" comparison. It also pays a client/server round-trip the embedded engines don't.
  • HoloDb runs both embedded (in-process) and as a networked TLS server (the fair peer to SQL Server's round-trip).
  • Why cents. Money is stored as integer minor units — the model every ledger uses. Integer SUM/COUNT are exact and constant-time from HoloDb's maintained accumulators; the queries it loses are the ones it has to scan for (top-K, filtered sums, high-cardinality and multi-column groups).

What the numbers say

HoloDb's maintained aggregates — the whole-ledger total and count, and the single-column GROUP BY rollups (revenue by status, month, region) — answer in microseconds and are constant-time: they read a kept tally instead of scanning, so they don't grow as the ledger does. HoloDb also wins the single-invoice lookup from its primary-key index. In-process it wins six of eleven; as a networked service against a disk-bound SQL Server it wins ten of eleven.

It loses the queries it has to scan for — ORDER BY … LIMIT top-K, filtered sums, and high-cardinality / multi-column groups (top customers over 500k IDs, region×status) — to DuckDB, an excellent pure-columnar engine. Shown above, not hidden. HoloDb's edge is the mixed transactional + analytics + vector workload, durable and larger-than-memory, in one embeddable dependency.
