The Pleroma: one array, every question

One array of exact integers holds your items. Ask it for counts by key, by flag word, by Hamming distance, by arrangement and by time. Apply a thousand operators in one pass.

What it is

The Pleroma is a fixed-size array of exact integers (finite-field arithmetic) that holds a multiset of items. Each item is a key, optionally with a flag word, an arrangement and a tick. One array answers many questions: counts by key, by flag word, by Hamming distance, by arrangement, by tick, and joint counts over any chosen faces.

The store holds a harmonic transform on the product of the key cycle, the flag cube, the symmetric group and the time cycle. Each component of the transform is a harmonic. The store keeps only the harmonics its views need, and each view reads its own slice of the array.

How the Pleroma was built

The three faces

A Pleroma view is one of three faces of the same array.

Syzygy (the key cycle, and the time cycle for tick views)
Key-addressed lookup: counts per key, whole items with signed counts, and the relation face. Key views refuse past KeyCapacity distinct keys, returning false rather than a wrong answer.
Monad (the arrangements, S_k, 2 to 5 things)
Counts per arrangement, even minus odd, tick maps, and the composition and conjugation of arrangements.
Ouroboros (the flag cube, up to 16 bits)
Counts per flag word, Hamming retrieval, Boolean predicates through the Walsh spectrum, bit maps and parity.

The pyramid

The operations form a grid of 8 rungs by 3 faces, plus one read-time operation (the lid): 25 cells in all. Every cell is a public member of Pleroma, checked against a brute-force or naive rebuild of the same answer, and every whole-store operation applies to all items in one pass.

Turn the pyramid, select a cell, or colour it by kind. Each cell shows its API and what it was checked against.

One store, many items

One Pleroma holds many items at once. Every whole-store operation applies to all of them in a single pass, and the cost of that pass does not depend on the number of items stored. A mix of different harmonic permutations (key scaling, bit maps and conjugation, rung 5) costs one pass per term.

The example holds three items with key capacity 4, then applies one kernel of 1x identity plus 2x (flip flag bit 0, age 1 tick). Press Replay to watch the pass move through the store, or switch between the counts before and after.

The kernel applies exactly the store you would get by moving every item by every element and adding the copies. The measured cost of the pass is on the evidence page, beside the cost of doing it item by item.

The code behind the example
using Phasor;

var store = new Pleroma(new HologramShape
{
    KeyCapacity = 4,
    FlagBits = 3,
    TimePeriod = 7,
    JointFaces = HologramFaces.Flags | HologramFaces.Time,
});
store.Add(new HologramItem(Key: 10, Flags: 0b001, Time: 0), 3);
store.Add(new HologramItem(Key: 20, Flags: 0b010, Time: 2), 2);
store.Add(new HologramItem(Key: 30, Flags: 0b100, Time: 4), 1);
Console.WriteLine("before flags " + string.Join(" ", store.Flags()));
Console.WriteLine("before times " + string.Join(" ", store.Times()));

// One kernel: 1x identity plus 2x (flip flag bit 0 and age one tick), applied to every item in one pass.
var kernel = new PleromaKernel(store.Shape);
kernel.Add(weight: 1L);
kernel.Add(flagMask: 0b001, timeShift: 1, weight: 2L);
store.Apply(kernel);

Console.WriteLine("after flags  " + string.Join(" ", store.Flags()));
Console.WriteLine("after times  " + string.Join(" ", store.Times()));
Output
before flags 0 3 2 0 1 0 0 0
before times 3 0 2 0 1 0 0
after flags  6 3 2 4 1 2 0 0
after times  3 6 2 4 1 2 0

Costs and checks

The capacity rule: 2K+1, and the refusal

A Pleroma with key capacity K stores exactly 2K+1 harmonics per key line. Any store of K or fewer keys is decoded exactly, by Berlekamp-Massey syndrome decoding as in Reed-Solomon codes. All K items are held at once in one 2K+1 entry array, and reading any face (flags, arrangements, times) gives exact counts for all of them.

Past capacity, decoding fails at K+1 keys and returns false instead of guessing, so the store never returns a wrong answer. Add keys below to see what the package returned for each number of distinct keys.

Bind and Attend

store.Bind(other) binds every pair of items from two stores in one pass: keys add (mod the key space), flags XOR, arrangements compose, ticks add and counts multiply. The cost is one matrix product per order representation, not per pair of items.

Attend(query, face) reads three things from one contraction of the store for a flag predicate (an exact match, a partial match on a mask, or any Boolean function). Counts per value are the exact counts at each matched flag word, arrangement or tick. Shares are those counts divided by the total, summing to 1. Parity is the sign of the total. The cost is one spectrum and one inner product, whatever the number of items.

Bind with a one-item store
using Phasor;

var shape = new HologramShape { KeyCapacity = 8, FlagBits = 4, TimePeriod = 9 };
var store = new Pleroma(shape);
store.Add(new HologramItem(Key: 10, Flags: 0b0011, Time: 2), 3);
store.Add(new HologramItem(Key: 20, Flags: 0b0111, Time: 5), 1);

// Bind with a one-item store: every item moves by the same key, flags and time shift.
var shift = new Pleroma(shape);
shift.Add(new HologramItem(Key: 1, Flags: 0b0001, Time: 1));
store.Bind(shift);

if (store.TryItems(out var items))
    foreach (var (item, count) in items)
        Console.WriteLine($"{item.Key}: flags {item.Flags}, time {item.Time}, count {count}");
Output
11: flags 2, time 3, count 3
21: flags 6, time 6, count 1

Keys, bit maps and exact checks

Shift, scale and combine keys
ShiftKeys(k) adds k to every key in place. ScaleKeys(u) multiplies every key by a unit, or gathers several keys to one for a non-unit. CombineCycles(a, b) joins two stores on coprime key cycles by the Chinese remainder theorem. Scaling and combining need the optional CompleteKeys configuration.
Frobenius and shift registers
Frobenius(modulus, steps) squares every flag word as a polynomial over GF(2), and ShiftRegister(polynomial, steps) steps every word through a linear shift register, each exactly and in one pass.
Exact repair and redundancy
ReservedKeys lets Verify detect and Repair rebuild up to r lost or corrupted key-line harmonics. CheckPrime mirrors every cell in a second prime so VerifyCheck detects any corruption of one copy. PleromaParity keeps the exact sum of a group of stores and rebuilds any one lost store.
Dense and sparse pages
With CompleteKeys, a store is a dense page of up to 4,096 slots where Count and Counts read every slot exactly in one transform. PleromaSparsePage holds exact counts over keys anywhere in a huge key set in memory proportional to the keys present.

Built on the Pleroma

The HoloDb holographic plane uses the Pleroma as its data store. COUNT, SUM, MIN, MAX, GROUP BY, HAVING, COUNT DISTINCT, WHERE, JOIN and any Boolean predicate are exact on it.

Limits

Keys
The key view is exact recovery of a multiset of keys, not similarity search. Capacity K keeps 2K+1 harmonics per key line and decodes up to K distinct keys.
Range
Counts are exact within the field's signed range, about 1.15 x 10^18 on the default field. No read detects a wrap past that range.
Kernels
A kernel is refused on a store with a check prime.
Hardware
The Pleroma runs on the CPU. There is no GPU kernel.
Speed
Exact arithmetic is not faster than a float bundle for a single read. The Pleroma gives you exactness and many views on one array.
Relations
Locating the contradiction on a relation face is not provided.
