The Pleroma: one array, every question

What it is

The Pleroma is a fixed-size array of exact integers (finite-field arithmetic) that holds a multiset of items. Each item is a key, optionally with a flag word, an arrangement and a tick. One array answers fifty different questions, each in a single pass: counts by key, by flag word, by Hamming distance, by arrangement, by tick, and joint counts over any chosen faces.

The store holds a harmonic transform on the product of the key cycle, the flag cube, the symmetric group and the time cycle. Each component of the transform is a harmonic. The store keeps only the harmonics its views need, and each view reads its own slice of the array.

How the Pleroma was built

The three faces

A Pleroma view is one of three faces of the same array.

Syzygy (the key cycle, and the time cycle for tick views)
Key-addressed lookup: counts per key, whole items with signed counts, and the relation face. Key views refuse past KeyCapacity distinct keys, returning false rather than a wrong answer.
Monad (the arrangements, S_k, 2 to 5 things)
Counts per arrangement, even minus odd, tick maps, and the composition and conjugation of arrangements.
Ouroboros (the flag cube, up to 16 bits)
Counts per flag word, Hamming retrieval, Boolean predicates through the Walsh spectrum, bit maps and parity.

The pyramid

The operations form a grid of 8 rungs by 3 faces, plus one read-time operation (the lid): 25 cells in all. Every cell is a public member of Pleroma, checked against a brute-force or naive rebuild of the same answer, and every whole-store operation applies to all items in one pass.

Turn the pyramid, select a cell, or colour it by kind. Each cell shows its API and what it was checked against.

One store, many items

One Pleroma holds many items at once. Every whole-store operation applies to all of them in a single pass, and the cost of that pass does not depend on the number of items stored. A mix of different harmonic permutations (key scaling, bit maps and conjugation, rung 5) costs one pass per term.

The example holds three items with key capacity 4, then applies one kernel of 1x identity plus 2x (flip flag bit 0, age 1 tick). Press Replay to watch the pass move through the store, or switch between the counts before and after.

The kernel applies exactly the store you would get by moving every item by every element and adding the copies. The measured cost of the pass is on the evidence page, beside the cost of doing it item by item.

The code behind the example
using Phasor;

var store = new Pleroma(new HologramShape
{
    KeyCapacity = 4,
    FlagBits = 3,
    TimePeriod = 7,
    JointFaces = HologramFaces.Flags | HologramFaces.Time,
});
store.Add(new HologramItem(Key: 10, Flags: 0b001, Time: 0), 3);
store.Add(new HologramItem(Key: 20, Flags: 0b010, Time: 2), 2);
store.Add(new HologramItem(Key: 30, Flags: 0b100, Time: 4), 1);
Console.WriteLine("before flags " + string.Join(" ", store.Flags()));
Console.WriteLine("before times " + string.Join(" ", store.Times()));

// One kernel: 1x identity plus 2x (flip flag bit 0 and age one tick), applied to every item in one pass.
var kernel = new PleromaKernel(store.Shape);
kernel.Add(weight: 1L);
kernel.Add(flagMask: 0b001, timeShift: 1, weight: 2L);
store.Apply(kernel);

Console.WriteLine("after flags  " + string.Join(" ", store.Flags()));
Console.WriteLine("after times  " + string.Join(" ", store.Times()));
Output
before flags 0 3 2 0 1 0 0 0
before times 3 0 2 0 1 0 0
after flags  6 3 2 4 1 2 0 0
after times  3 6 2 4 1 2 0

Costs and checks

The capacity rule: 2K+1, and the refusal

A Pleroma with key capacity K stores exactly 2K+1 harmonics per key line. Any store of K or fewer keys is decoded exactly, by Berlekamp-Massey syndrome decoding as in Reed-Solomon codes. All K items are held at once in one 2K+1 entry array, and reading any face (flags, arrangements, times) gives exact counts for all of them.

Past capacity, decoding fails at K+1 keys and returns false instead of guessing, so the store never returns a wrong answer. Add keys below to see what the package returned for each number of distinct keys.

Bind and Attend

store.Bind(other) binds every pair of items from two stores in one pass: keys add (mod the key space), flags XOR, arrangements compose, ticks add and counts multiply. The cost is one matrix product per order representation, not per pair of items.

Attend(query, face) reads three things from one contraction of the store for a flag predicate (an exact match, a partial match on a mask, or any Boolean function). Counts per value are the exact counts at each matched flag word, arrangement or tick. Shares are those counts divided by the total, summing to 1. Parity is the sign of the total. The cost is one spectrum and one inner product, whatever the number of items.

Bind with a one-item store
using Phasor;

var shape = new HologramShape { KeyCapacity = 8, FlagBits = 4, TimePeriod = 9 };
var store = new Pleroma(shape);
store.Add(new HologramItem(Key: 10, Flags: 0b0011, Time: 2), 3);
store.Add(new HologramItem(Key: 20, Flags: 0b0111, Time: 5), 1);

// Bind with a one-item store: every item moves by the same key, flags and time shift.
var shift = new Pleroma(shape);
shift.Add(new HologramItem(Key: 1, Flags: 0b0001, Time: 1));
store.Bind(shift);

if (store.TryItems(out var items))
    foreach (var (item, count) in items)
        Console.WriteLine($"{item.Key}: flags {item.Flags}, time {item.Time}, count {count}");
Output
11: flags 2, time 3, count 3
21: flags 6, time 6, count 1

Flag reads, widening and tenants

Flags(bits) returns the exact count of each flag pattern on a chosen subset of the bits, with no store built. FlagsMany reads one bit set from several stores of one shape in one batched transform per prime, and FlagsUnion takes several bit sets. PleromaReadSet declares several reads and answers them in one call, and Run applies a kernel to clones of the stores before answering. Each read makes its own transform by default. ReadFlagWords returns the counts of a few words without the whole-store transform. WidenFlags(bits, at) inserts zero flag bits and copies the cells natively, with no decode. AddFlagWords adds many flag words in one pass over the cells.

A tenant takes bits in the high end of the flag word. The all-tenant total is Flags(data bits) on one store, and a tenant's own counts are its slice of Flags(tenant bits + data bits). Tenant bits plus data bits are capped at 16.

The kernel is the symmetry

A symmetry here is a move you can make to every item at once, such as flipping a flag, advancing the clock or reordering the arrangement. A kernel is a weighted mix of such moves, and the store applies the whole mix in one pass instead of one pass per move. This section says which moves can be mixed that way and which cannot. The numbers are how many of the store's 89 operations fall on each side.

The store holds the harmonic transform of its items on the product of four families: the key cycle Z_N (a cycle of N keys), the flag cube Z_2^m (m flag bits), the arrangements S_k (the orderings of k things) and the tick cycle Z_T (a cycle of T ticks). A harmonic is one component of that transform, and each stored item is one point of that product. A symmetry here is a translation of the product: add a key shift, XOR a flag mask, advance a tick, or multiply an arrangement. A weighted sum of translations is an element of the group algebra, and PleromaKernel holds exactly that element and applies it to every stored item in one pass. For a finite group, the linear maps that commute with its translations are exactly the group-algebra elements, so on the faces the kernel carries, the kernel is the general form of such a map.

Flag and tick faces
Every translation is a kernel element. Both are abelian, so their characters diagonalise every translation: a flag mask or a tick shift is one scalar on each harmonic block, and any weighted sum of them is one kernel. Bit permutations and sign flips of the flag word are not translations and are not kernel elements.
Arrangement face (S_2 to S_5 as built)
Left multiplication joins the kernel. A left arrangement element multiplies each irreducible block from the left, and weighted sums of those span every left multiplication. The right action, which relabels the other side of the block, and conjugation, which relabels both sides, are not kernel elements.
Key face
A key shift is a kernel element on a keyed kernel. PleromaKernel(shape, keyHarmonics: true) holds one factor per key harmonic, so AddKeyed puts a key shift in the same kernel as the flag, arrangement and tick elements, and one Apply runs the mix. ShiftKeys(k) gives the same store as a one-element keyed kernel. A keyed kernel holds one number per stored cell. Key scaling, Hadamard products and per-key weights are not kernel elements: each mixes key harmonics together, and no per-harmonic factor can hold that.

The measured boundary. The coverage record sorts the 89 operations that transform the store or read it by how they commute with the symmetry group. To commute with the group means that moving first and then applying the operation gives the same result as applying the operation first and then moving. A probe is a test that applies the operation to a store and to its moved copy, and compares the two. Some operations return a list, a count or a boolean, so each of those needs an output-action declaration first: a statement of how its output moves when its input is moved, which the probe needs before it can check the operation.

Joins here means: commutes with the group and lies on an axis the kernel carries (flag, left arrangement, tick, and the key harmonic of a keyed kernel). Kernel membership is stricter and counts only the 8 kernel operators in 8 of 39.

29 commute with every generator of the group
17 of them join the kernel's axes: 8 kernel operators (Tick, Diffuse, Apply, the four kernel methods and AddKeyed), 2 store sums (Add and Subtract of another store) and 7 reads of the flag face and the total, answered through a read set (Flags, Flags(bits), FlagsMany, FlagsUnion, Total, and PleromaReadSet Read and Run). The other 12 commute but lie off those axes: ShiftKeys (its kernel element is AddKeyed), Hadamard, Syndrome, and the reads on the key, arrangement, tick, joint and pair axes.
28 are linear or affine and break a named symmetry
For example a bit permutation of the flags, a key scaling, a Frobenius squaring or a bind.
17 are not linear
Choices, decodes, order statistics, draws and predicates, such as Sample, MinKey and Nearest.
15 need an output-action declaration
A probe cannot classify them until one is given. Among them are CombineCycles, TimeMap and Project, and the record gives the reason for each.
Commuting is necessary, not sufficient
ShiftKeys is the case that shows it: it commutes with the group, is not an element of an unkeyed kernel, and is an element of a keyed one. 66 of the 89 operations are checked by a probe run, and the others carry their reason in the record.

Keys, bit maps and exact checks

Shift, scale and combine keys
ShiftKeys(k) adds k to every key in place. ScaleKeys(u) multiplies every key by a unit, or gathers several keys to one for a non-unit. CombineCycles(a, b) joins two stores on coprime key cycles by the Chinese remainder theorem. Scaling and combining need the optional CompleteKeys configuration. On a keyed kernel a key shift is also a kernel element (AddKeyed).
Frobenius and shift registers
Frobenius(modulus, steps) squares every flag word as a polynomial over GF(2), and ShiftRegister(polynomial, steps) steps every word through a linear shift register, each exactly and in one pass.
Exact repair and redundancy
ReservedKeys lets Verify detect and Repair rebuild up to r lost or corrupted key-line harmonics. CheckPrime mirrors every cell in a second prime so VerifyCheck detects any corruption of one copy. PleromaParity keeps the exact sum of a group of stores and rebuilds any one lost store.
Dense and sparse pages
With CompleteKeys, a store is a dense page of up to 4,096 slots where Count and Counts read every slot exactly in one transform. PleromaSparsePage holds exact counts over keys anywhere in a huge key set in memory proportional to the keys present.

Built on the Pleroma

The HoloDb holographic plane uses the Pleroma as its data store. COUNT, SUM, MIN, MAX, GROUP BY, HAVING, COUNT DISTINCT, WHERE, JOIN and any Boolean predicate are exact on it.

Limits

Keys
The key view is exact recovery of a multiset of keys, not similarity search. Capacity K keeps 2K+1 harmonics per key line and decodes up to K distinct keys.
Range
Counts are exact within the field's signed range, about 1.15 x 10^18 on the default field. A plain read does not check for a wrap. On a store with a check prime, VerifyCheck detects one within the check bound.
Kernels
On a store with a check prime, a kernel runs through a mirror kernel in the check prime, built from the same elements. A kernel built from a shape without that check prime is refused.
Hardware
The Pleroma runs on the CPU. There is no GPU kernel.
Speed
Exact arithmetic is not faster than a float bundle for a single read. The Pleroma gives you exactness and many views on one array.
Reads
Each read makes its own transform by default. A transform is shared between reads only inside an internal planner that is not exposed.
Tenants and widening
Tenant bits plus data bits must be at most 16, and past that the tenants split across stores. WidenFlags refuses continuous components, relation faces and reserved keys, and any result above 16 flag bits.
Relations
Locating the contradiction on a relation face is not provided.
