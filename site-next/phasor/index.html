See the numbers

  • One pass, from 1 to 10,368 operators

    Apply took 0.17 to 0.44 ms per call over two runs, with no trend in the number of elements. Building the same store from the moved items took 3 ms at 1 element and 1,916 ms at 1,000. Conditions: a 10,464-cell store (GF(13,879), 6 flag bits, S_3, time period 27, joint flags by order by time, key capacity 4, a continuous component, 10 items on four keys), random kernels, the mean of 20 calls after one warm-up, Release build, a loaded i9-11950H.

  • 64 items recovered exactly

    At equal storage (about 2,000 to 2,600 bits), the exact key view recovered 64 items in 200 of 200 trials. The best float baseline reached 95 percent at 4 items. That is 16 times the items at these budgets. The benchmark is not part of the shipped package.

  • A clear no past capacity

    Past capacity (65 to 96 items), the keys-only hologram refused 12,800 of 12,800 trials with no wrong answer. Every float baseline answered wrongly every time.

  • A whole page in 0.6 ms

    With a complete key band, reading a 3,150-slot page costs about 0.6 ms (188 to 246 ns per slot). Building a page from a count vector is about 100 times faster than adding its keys one by one.

What you can build

Each one is in the package today.

  • Database answers in a millisecond

    Read a whole 3,150-slot page of exact counts in about 0.6 ms. HoloDb serves COUNT, SUM, GROUP BY and joins from slices of a store like this.

    See it inside HoloDb

  • Replicas that sync by their differences

    Send one small message sized to what differs, not to your data. Ten thousand shared items and one different on each side take 192 bytes, and the other side reads the exact difference.

  • A store that repairs itself

    Lose up to five values and get them back, 300 of 300 times. Catch one corrupted cell in either copy, 10,000 of 10,000 times. Rebuild a lost store from its group, 100 of 100 times.

  • A memory that reads exactly

    Store pairs and read them back without drift. At equal storage, recall held at 100 percent from 2 to 32 pairs, where a float bundle fell to 21.9 percent at 32.

  • Age and reshape everything at once

    Age, relabel, diffuse or bind every item in one pass. The cost follows the size of the store, not the number of items in it.

  • Any question, one read

    Count the items that match any condition on their flags, however tangled, in one read. Ask for counts, shares and parity from one query.

Run it yourself

The program behind the demo above.

Add three items, sum two operators into one kernel, apply it once and read the counts. This is the whole program, compiled and run against the published package.

C#
using Phasor;

var shape = new HologramShape { KeyCapacity = 4, FlagBits = 3, TimePeriod = 7, JointFaces = HologramFaces.Flags | HologramFaces.Time };
var store = new Pleroma(shape);                          // 96 cells for this shape, whatever the item count
store.Add(new HologramItem(Key: 10, Flags: 0b001, Time: 0), 3);
store.Add(new HologramItem(Key: 20, Flags: 0b010, Time: 2), 2);
store.Add(new HologramItem(Key: 30, Flags: 0b100, Time: 4), 1);

if (store.TryItems(out var items))
    foreach (var (item, count) in items)
        Console.WriteLine($"key {item.Key} flags {item.Flags} time {item.Time} count {count}");

var kernel = new PleromaKernel(shape);
kernel.Add(weight: 1L);                                  // keep every item
kernel.Add(flagMask: 0b001, timeShift: 1, weight: 2L);   // and twice: flip bit 0, age one tick
store.Apply(kernel);                                     // one pass over all 96 cells

if (store.TryKeys(out var keys))
    foreach (var k in keys)
        Console.WriteLine($"key total {k}");
Console.WriteLine(string.Join(" ", store.Flags()));
Console.WriteLine(string.Join(" ", store.Times()));

Flag reads, widening and tenants

Read a few bits, grow a store, share one store between tenantsEvery flag example, with its output

The flag face is the row of yes or no bits kept with every item. These operations read just the bits you name, read them across many stores in one call, add bits to a store that already holds data, and keep several tenants apart inside one store. None of them builds a second store to do it.

  • Read only the bits you name

    Flags(bits) returns the exact count of each flag pattern on the bits you name and sums out every other bit. The empty list returns the total. No store is built.

  • Many stores, one call

    Pleroma.FlagsMany(stores, bits) reads one bit set from several stores of one shape in one batched transform per prime, cell for cell equal to one Flags(bits) per store, and FlagsUnion takes several bit sets. PleromaReadSet declares each read once and answers all of them for all stores in one call, and Run applies a kernel to clones of the stores first. Each read makes its own transform by default, and the time still grows with the number of planes, because the output does.

  • A few words, cheaply

    ReadFlagWords returns the exact count of each word you list. Up to four words it sums the flag cells once per word, and above four it uses the whole-store transform. Both return the same numbers. Recorded at 14 flag bits (Release build, loaded machine, medians): about 134 microseconds for one word and about 90 more for each further word, against 0.66 milliseconds for the whole-store transform.

  • Widen a store without rebuilding it

    WidenFlags(bits, at) returns a store with zero flag bits inserted at a position, and the source is unchanged. The cells are copied through a cached map, so no item is decoded or added again. It refuses continuous components, relation faces and reserved keys, and the result may hold at most 16 flag bits.

  • Add many flag words in one pass

    AddFlagWords adds counts[j] copies of words[j] at one key in one pass over the cells, equal to one Add per word. The static overload applies one batch to several stores of one shape. Recorded at 14 flag bits: one word about 80 microseconds, sixteen words about 215 to 237 microseconds.

  • Tenants as flag bits

    Give each tenant bits in the high end of the flag word and the data the low bits. The all-tenant total is Flags(data bits) on that store, one transform whatever the tenant count. A tenant's own counts are its slice of Flags(tenant bits + data bits), whose transform grows with the tenant count. The cap is 16 flag bits in total: six data bits leave ten tenant bits, which is 1,024 tenants by arithmetic, and ten data bits leave six, which is 64. The recorded run reached 32 tenants. Past the cap, split the tenants across stores.

Read only the bits you name

C#
using Phasor;

var store = new Pleroma(new HologramShape { FlagBits = 3 });

long[] onBits02 = store.Flags(new[] { 0, 2 });

Where things sit in superposition

Data and operators, in one array

The Pleroma holds many items at once as signed counts in one array, and a kernel holds many operators at once as one table. One pass applies the table to the array. The array is set by the shape, not by how many items go in.

Data

Each question reads its own slice of the array, so every view comes from the same store.

Keys and whole items
TryKeys and TryItems return exact counts and refuse past KeyCapacity distinct keys.
Flags and closeness
Flags() counts every flag word. Near counts the items within r bits of a word, and Nearest returns the closest stored words.
Arrangements
Exact counts for every arrangement of up to 5 things, and the even-minus-odd balance.
Time
The exact count at every tick.
Joint counts
Exact counts over any mix of flags, order and time that the shape stores.
Any predicate
CountWhere counts the items whose flags satisfy any condition, with one inner product.
One query, three reads
Attend returns exact counts, shares that sum to 1 and the parity, from one contraction.

Operators

PleromaKernel sums weighted operators into one kernel. store.Apply(kernel) moves every item by every operator in one pass over the array. The result is exactly the store you would get by moving each item by each element and adding the copies.

Join a kernel

  • flag XOR masks (flagMask)
  • arrangements by left multiplication (arrangement)
  • time shifts (timeShift)
  • key shifts on a keyed kernel (AddKeyed, with PleromaKernel(shape, keyHarmonics: true))
  • Diffuse (the two-element kernel: stay with weight a, move one tick with weight b minus a)
  • sums of kernels (Add(PleromaKernel)) and products (PleromaKernel.Compose, block by block)

Cost one pass each in a mix

  • key scaling (ScaleKeys)
  • right relabelling of arrangements, and conjugation
  • bit maps on the flag cube (Frobenius, ShiftRegister)
  • sign flips of flag words (signs shift the Walsh index)

A weighted mix of operators that do not join a kernel costs one pass per term. Powers of one such operator compose into one pass.

Exact, and it says no

With KeyCapacity K, each key line keeps 2K+1 numbers and decodes up to K distinct keys. Past K the key reads refuse. Every other read is exact at any load while each count stays inside the field's signed range, about 1.15 x 10^18 on the default field.

Walk the pyramid

The kernel is the symmetry

Which moves mix into one pass, and which do not

A symmetry here is a move you can make to every item at once, such as flipping a flag, advancing the clock or reordering the arrangement. A kernel is a weighted mix of such moves, and the store applies the whole mix in one pass instead of one pass per move. This section says which moves can be mixed that way and which cannot. The numbers are how many of the store's 90 operations fall on each side.

Joins here means: commutes with the group and lies on an axis the kernel carries (flag, left arrangement, tick, and the key harmonic of a keyed kernel). The 17 that join are 8 kernel operators (Tick, Diffuse, Apply, the four kernel methods and AddKeyed), 2 store sums (Add and Subtract of another store) and 7 reads of the flag face and the total, answered through a read set (Flags, Flags(bits), FlagsMany, FlagsUnion, Total, and PleromaReadSet Read and Run). The other 12 commute but lie off those axes: ShiftKeys (its kernel element is AddKeyed), Hadamard, Syndrome, and the reads on the key, arrangement, tick, joint and pair axes.

Kernel membership is stricter and counts only the 8 kernel operators in 8 of 40. Commuting with the group is necessary for kernel membership and not sufficient: on an unkeyed kernel ShiftKeys commutes and is not an element, and a keyed kernel is what makes it one. 67 of the 90 are checked by a probe run, and the others carry their reason in the record.

By face

Flag and tick faces
Every translation is a kernel element. Both are abelian, so their characters diagonalise every translation: a flag mask or a tick shift is one scalar on each harmonic block, and any weighted sum of them is one kernel. Bit permutations and sign flips of the flag word are not translations and are not kernel elements.
Arrangement face (S_2 to S_5 as built)
Left multiplication joins the kernel. A left arrangement element multiplies each irreducible block from the left, and weighted sums of those span every left multiplication. The right action, which relabels the other side of the block, and conjugation, which relabels both sides, are not kernel elements.
Key face
A key shift is a kernel element on a keyed kernel. PleromaKernel(shape, keyHarmonics: true) holds one factor per key harmonic, so AddKeyed puts a key shift in the same kernel as the flag, arrangement and tick elements, and one Apply runs the mix. ShiftKeys(k) gives the same store as a one-element keyed kernel. A keyed kernel holds one number per stored cell. Key scaling, Hadamard products and per-key weights are not kernel elements: each mixes key harmonics together, and no per-harmonic factor can hold that.
What commute, probe and declaration mean

To commute with the group means that moving first and then applying the operation gives the same result as applying the operation first and then moving. A probe is a test that applies the operation to a store and to its moved copy, and compares the two. Some operations return a list, a count or a boolean, so each of those needs an output-action declaration first: a statement of how its output moves when its input is moved, which the probe needs before it can check the operation.

The store holds the harmonic transform of its items on the product of four families: the key cycle Z_N (a cycle of N keys), the flag cube Z_2^m (m flag bits), the arrangements S_k (the orderings of k things) and the tick cycle Z_T (a cycle of T ticks). A harmonic is one component of that transform, and each stored item is one point of that product. A symmetry here is a translation of the product: add a key shift, XOR a flag mask, advance a tick, or multiply an arrangement. A weighted sum of translations is an element of the group algebra, and PleromaKernel holds exactly that element and applies it to every stored item in one pass. For a finite group, the linear maps that commute with its translations are exactly the group-algebra elements, so on the faces the kernel carries, the kernel is the general form of such a map.

Its structure follows three families of symmetry, taken in a fixed order: the cyclic key group, the flag cube Z_2^m and the symmetric group S_k. The time cycle is a cyclic family of the same kind. The eight rungs run in that order, and each one adds operations to those before it. Every operation is checked against a brute-force rebuild of the same answer.

Put it to work

Four uses, each with its limit

  • HoloDb aggregate plane

    Database.EnablePleroma(table, options) derives a Pleroma from a table's columns and serves COUNT, SUM, GROUP BY, WHERE, COUNT DISTINCT, MIN and MAX of dimensions, HAVING, and a single equi-join COUNT or SUM from exact slices. It holds in-RAM tables and is not persisted, so call it again after Open. AVG and other shapes use the engine.

    HoloDb on the Pleroma

  • Page store, larger than memory

    Pages of one shape are stored as records with a check prime that verifies every record, parity groups that rebuild one lost record each, restore points, and journal numbers so replay applies each add once. It needs a complete key band, and a reader may see a batch half applied while it runs.

    HoloDb on the Pleroma

  • Replica reconciliation

    Two replicas each hold a CycleHologram. The one with the difference sends its hologram, and the other subtracts its own and decodes the exact signed difference. The message is sized to the difference, not to the data. It decodes when the difference has at most the capacity's worth of distinct symbols, so size the capacity to the largest difference you expect.

    C#
    using Phasor;

var a = new CycleHologram(capacity: 4);
var b = new CycleHologram(capacity: 4);
for (ulong id = 0; id < 10_000; id++) { a.Add(id); b.Add(id); }
a.Add(777_001);        // only on A
b.Add(777_002, 2);     // only on B, two copies

byte[] wire = a.Serialize();                   // what A sends
Console.WriteLine($"wire size {wire.Length} bytes");
var delta = CycleHologram.Deserialize(wire);
delta.Subtract(b);                             // B subtracts its own hologram: A minus B
if (delta.TryDecode(out var diff))
    foreach (var (symbol, count) in diff.OrderBy(d => d.Item1))
        Console.WriteLine($"{symbol}: {count}");
    Output
    wire size 192 bytes
777001: 1
777002: -2

  • Batch relabel, age and diffuse

    Tick, Diffuse, RelabelFlags, RelabelArrangements, ShiftKeys, ScaleKeys (on a complete key band) and Apply(kernel) each act on every stored item at once. A mix of different harmonic permutations costs one pass per term. Key shifts join a keyed kernel. Diffuse readbacks need TimeScale times the total to stay within half the field.

When another tool fits better

  • A single item, or a few keys. Each Add touches every cell of the store. A dictionary is cheaper for one lookup, and the sparse page (PleromaSparsePage) suits a few keys.
  • Floating-point similarity at high dimension. The Pleroma is exact and has no key-addressed similarity. For graded similarity use the continuous component (ContinuousFade) or the HoloCodec similarity search.
  • More distinct keys than the capacity, without a bigger shape. The key view refuses past KeyCapacity. Raising it costs 2K+1 numbers per key line.
  • Choices. argmax, softmax and sampling are not linear, so they are read-time steps (Attend's shares, Sample), not kernel elements.
  • Counts past the field's range. Weighted kernels on a small field need headroom. On a large field the limit is about 1.15 x 10^18 per count.

Know before you start

  • The key view is exact recovery of a multiset of keys, not similarity search. There is no key-addressed attention.
  • Counts are exact within the field's signed range. A plain read does not check for a wrap. On a store with a check prime, VerifyCheck detects one within the check bound.
  • The Pleroma runs on the CPU. There is no GPU kernel.
  • Exact arithmetic is not faster in general. A Pleroma read costs one or more transforms, and a float bundle read is one correlation. The Pleroma gives you exactness and many views on one array.
  • On a store with a check prime, a kernel runs through a mirror kernel in the check prime, built from the same elements. A kernel built from a shape without that check prime is refused.
  • Locating the contradiction on a relation face is not provided.
  • A read set returns many reads in one call, but each read makes its own transform by default. A transform is shared between reads only inside an internal planner that is not exposed.
  • Tenants as flag bits share one store only while tenant bits plus data bits stay at 16 or fewer.
  • WidenFlags refuses continuous components, relation faces and reserved keys, and any result above 16 flag bits.

Underneath: the phasor codec

Numbers and symbols as unit-complex facesCodec and Pleroma docs

The codec encodes numbers and symbols as unit-complex faces and composes them with bind, unbind, bundle and correlate. On the linear band of a face, bind adds the values. On the log band, it multiplies them. PhasorCodec is fixed-width and built for neural models. HoloCodec is configurable in width, uses SIMD over a planar layout and is built for storage and similarity search. The two layouts do not mix.

C#
using Phasor;

// Encode a number and some symbols
double[] five = PhasorCodec.Encode("5");
double[] three = PhasorCodec.Encode("3");
double[] age = PhasorCodec.Encode("age");
double[] name = PhasorCodec.Encode("name");
double[] hello = PhasorCodec.Encode("hello");

// Bind two numbers: adds them on the linear band
double[] fivePlusThree = PhasorCodec.Bind(five, three);
Console.WriteLine($"5 + 3 = {PhasorCodec.DecodeSum(fivePlusThree, max: 10)}");

// Bind each value to a role, bundle the pairs into one record, then unbind a role to read its value back
double[] record = PhasorCodec.Bundle(PhasorCodec.Bind(age, five), PhasorCodec.Bind(name, hello));
double[] ageField = PhasorCodec.Unbind(record, age);
Console.WriteLine($"age field matches 5 better than 3: {PhasorCodec.Correlate(ageField, five) > PhasorCodec.Correlate(ageField, three)}");

// For larger workloads and similarity search, HoloCodec is SIMD and configurable in width
var codec = new HoloCodec(dim: 1024);
double[] encoded = codec.Encode("hello");
Console.WriteLine($"HoloCodec self-similarity is positive: {HoloCodec.Dot(encoded, codec.Encode("hello")) > 0}");
Output
5 + 3 = 8
age field matches 5 better than 3: True
