HoloDb benchmarks

Totals over 100,000,000 invoices in 0.12 ms and four joins to two million customers in 0.19 to 0.25 ms, against tuned DuckDB and tuned SQL Server on the same machine and data. Out of the box, scans that no structure covers are slower, and the chart shows each of them as an amber bar.

How we measured

Stated once, for every figure on this page
Machine
An 11th Gen Intel Core i9-11950H at 2.60 GHz, 16 logical cores, 34.1 GB of memory, Windows 11, .NET 8.0.27. Each engine ran in its own process.
Data and queries
100,000,000 invoices and 2,000,000 customers; 16 billing queries: five rollups, a lookup, five scans and five joins to the customers.
Tuned DuckDB
DuckDB 1.5.5: table written in customer_id order, ANALYZE, 16 threads, 12 GB memory limit.
Tuned SQL Server
SQL Server 2022 Developer: a columnstore index, a descending index on amount_cents and indexed views, max server memory 5,120 MB, in a container.
Tuning
We chose the rivals' tuning after a 10,000,000-row trial and fixed it before the 100,000,000-row build. A different tuning is untested.
Same answers
Before any query is timed, its rows are hashed. All four arms return identical results on all 16 queries, including where HoloDb is slower.
Warm and cold
Warm is the median of three runs. Cold is the first run after the file cache was cleared by reading a 34 GB file (for SQL Server, dropping its buffers).
Repeats
Each engine ran the whole set twice. A tilde marks a figure whose repeat differed by more than 20 percent, and a query counts as ahead or behind only when both runs agree.

What HoloDb does not do

Each row is true today
What is true today
AreaWhat is true today
JoinsINNER JOIN only. Several in one statement on in-memory tables, one on a paged table. LEFT, RIGHT, FULL, CROSS, NATURAL, USING and comma joins are refused.
AliasesNo AS on columns or tables. Aggregate columns are named agg(col), such as count(*).
ALTER TABLEADD COLUMN only, with a DEFAULT or NULL. No DROP COLUMN, RENAME COLUMN or RENAME TO.
ExpressionsNo CASE, LENGTH(), OFFSET or UNION, and no arithmetic in the select list or inside SUM(v * 2). COUNT(DISTINCT col), LIKE and IN (SELECT ...) work on in-memory tables.
MoneyConstant-time totals are for INT columns. REAL SUM is a SIMD scan, and DECIMAL and NUMERIC are REAL (a double), so hold money as integer cents. There is no fixed-point type.
Saved summariesA summary made with CREATE INDEX ... USING SUMMARY, or built by the planner, is saved with the table and restored on open. A plane attached with the EnablePleroma call on an in-memory table is not saved: call it again after Open.
Summary limitsA declared summary takes up to 4,095 distinct values per column (1,024 for one the planner builds) and a joint of 12 bits. A column over its limit goes to a scan and is never approximated.
Joins on paged tablesThe keyed summary holds up to 4,194,304 consecutive INT keys. The 100,000,000-invoice run joins 2,000,000 customers.
LanguagesA .NET library. The server speaks a TCP and TLS binary protocol whose only client is .NET. No JDBC, ODBC, Python, Node or Go client, and no PostgreSQL or MySQL wire.
ConcurrencyOne process per database and one writer at a time. Simple aggregate reads run off a snapshot without the lock. A second process cannot open a paged database's files, and there is no MVCC: a long transaction blocks other writers.
Table sizeTested to 100,000,000 rows (4.94 GB paged, 165 s to load). In-memory tables are bounded by RAM at about 110 bytes per row. A paged primary key loaded out of order keeps a RAM dictionary of about 35 bytes per row. Beyond 100,000,000 rows is untested.
BackupOffline: copy the files of a closed database. There is no online backup and no point-in-time recovery.
Crash safetyOne fsync per commit. Tests cut the log at every record boundary, flip bits in the log and the data file, and tear a page during a checkpoint. A real power cut, a disk that lies about fsync, a full disk and several processes are not tested.
