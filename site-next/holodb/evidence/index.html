How HoloDb is tested

A wrong answer is the one failure a database cannot afford, so the tests try to make HoloDb wrong and report the first time it is. The page states what is tested and how to run the checks. It carries no measured figures.

What it costs

Every loss in this record, stated once
  • Structures help repeated work. A filter whose matching rows are spread evenly over every block gains nothing from learned records.
  • Moving scattered rows costs time per row moved, so a scattered filter pays it back only after repeated use.
  • The tests check correctness. They publish no timings, so this page makes no speed claim.

How it was measured

Stated once, for every figure on this page
Workload
The battery runs its specs in both pipeline modes. The chaos runs generate random SQL streams over a paged table. The customer lifecycle test grows one database from an empty file over many separate processes.
Engines
HoloDb; SQLite as the oracle for every answer, the full row set and the table seal
Check
Every SELECT, the full row set and the table seal are compared with SQLite, and the database is opened again after every session. Every check has a mutant arm that breaks the engine on purpose, and the check must go red for the right reason.
Statistic
Counts of blocks, pins, runs and bytes are exact. A pin is one page read through the buffer pool, and counts of pins stand in for time.
Memory and logging
Three terms recur. A block is a run of rows stored together. A page is 8 KB of file. A pin is one page read through the buffer pool.

What we test

A wrong answer is the one failure a database cannot afford, so the tests try to make HoloDb wrong and report the first time it is.

The kinds of test
TestWhat it does
The batteryA battery of specs runs in both pipeline modes: the block pipeline, which reads and learns from blocks, and the analytic executor, which answers from exact totals. A spec covers one area of the engine: NULL logic, the block map, crash points, the history log, AS OF, the indexes and summaries, learned records, transactions and their undo, the budget, and randomized streams. Several specs run at 3,000,000 rows.
Red armsChecks have mutant arms: a deliberately broken engine, such as an update that leaves a stale sum or a log that drops a record, that the check must catch for the right reason.
Chaos runschaos2 generates random SQL streams over a paged table: SELECT with filters, grouping, joins and top-k, INSERT, UPDATE, DELETE, transactions with rollback, ALTER, index DDL, reopen, power loss, a power cut at a durable write inside COMMIT, and a restart with builds running. SQLite is the oracle for every answer, for the full row set, and for the table seal.
Customer lifecycleA simulated customer starts with an empty file and works one database across many separate processes: cold open, imports, daily batches, updates, retention deletes, ALTER, index DDL, repeated dashboards, ad hoc SQL, transactions with rollback, power cuts in process, and hard kills of the process by its parent. A SQLite mirror is the oracle, and the database is opened again after every session.

How to run the checks

The checks run from the package's source repository, not from this site. The HoloDb.Bench project runs them as verbs: the verb name is its argument, for example dotnet run -c Release --project HoloDb.Bench -- sqlcore. Each verb exits 0 when its checks pass. The verbs include sqlcore, sqlsurface, sqlrefuse, asofcrash, stmtatomic, pagedcrash, walepoch, decimalcore and chaos2.

The SQL surface is checked by sqlsurface, sqlcore and sqlrefuse. The history log is checked by asofcrash, the write path by stmtatomic and pagedcrash, and the DECIMAL type by decimalcore.

Limits

  • The lifecycle and crash guarantees are tested at 3,000,000 rows. The limits on the HoloDb page list the rest.
