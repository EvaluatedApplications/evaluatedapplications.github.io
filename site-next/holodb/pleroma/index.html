HoloDb, built on Pleroma

Ask a table a question without reading the table.

Switch on the plane for a table and HoloDb answers filters, group-bys, distinct counts and joins from a small exact summary instead of scanning rows. It is optional, off until you ask, and every answer matches the engine's.

See the numbers, and what the plane costs

  • Rollups on the billing ledger

    Overdue outstanding falls from 5.93 ms to 0.01 ms, and revenue by region and status from 32.30 ms to 0.18 ms. Building the plane for 10,000,000 rows took 741 ms and its cells take 34,528 bytes. All 16 results were identical across the engines.

  • A live dashboard of 10,000,000 events

    Across nine scalar filter slices the median speed-up over the engine is 121.40 times, and 191.5 times over the best of out-of-the-box SQLite, DuckDB and SQL Server (default settings, no added indexes, no summary tables). Group-bys gain 20.90 times, HAVING 24.57 times and distinct or min and max with a filter 18.42 times. Queries the plane declines tie with the engine at 0.97 times.

  • Write, then read, as the table grows

    One insert followed by the same two-column group-by costs 385, 343 and 354 microseconds with the plane at 100,000, 300,000 and 1,000,000 rows, and 1.03, 1.44 and 3.54 milliseconds for the engine alone. A placebo pair that both arms run the same way reads 1.04, 1.03 and 0.97. Conditions: Release build, a 16-core laptop CPU (Intel Core i9-11950H) with nothing else heavy running, 200 pairs at each size.

  • What it costs

    Writes cost more with the plane attached: a 10,000-row bulk load takes 11.62 ms against 9.85 ms, and 200 single-row inserts take 1.55 ms against 1.23 ms. On a table of 1,000,000 rows the plane is slower than the engine on whole-table counts and sums, single-column group-bys, and minimums and maximums, because the engine already reads a maintained total there in microseconds. A join that is not a repeat usually costs more through the plane than the engine's own join.

HoloDb deep dive

What Pleroma gives HoloDb

HoloDb is built with Pleroma, the exact count-and-sum structure in the Phasor package. Three parts of HoloDb are Pleroma parts. This page says what each gives you and what it costs. The first two are optional and off until you ask for them.

Engine results and plane results

The 10,000,000-invoice comparison against engines as they ship ran on the HoloDb engine alone, with no plane attached, and the 100,000,000-invoice comparison uses summaries that are declared or built by the planner. The plane is a separate, opt-in feature, measured in its own runs in the deep dive, where its costs sit beside its wins.

Plane results and costs

The aggregate plane: exact answers from a derived summary

You name a few small-domain columns (dimensions, INT or TEXT) and the INT columns to sum (measures). HoloDb keeps a Pleroma summary of them, updated by every write, and answers filters, multi-column GROUP BY, COUNT(DISTINCT), MIN and MAX of a dimension, and equi-join COUNT and SUM from it, without scanning the table.

Exact and derived
The columns stay the source of truth, and the plane is rebuilt from them. PleromaVerify rebuilds it and compares, and returns nothing when they agree. Sums are held exactly past 64 bits: the plane raises an error rather than wrap, and PleromaSumExact returns the exact 128-bit total.
It declines safely
Anything the plane does not hold (AVG, a column that is not a dimension or measure, a dimension over its cap of distinct values, a join over 4,095 keys) goes to the engine, so a query returns the same rows with the plane on or off. The default routing, PleromaMode.Auto, also leaves to the engine the shapes where it already reads a maintained total (whole-table counts and sums, single-column GROUP BY) and GROUP BY with a WHERE below 140,000 rows, because the engine is faster there.
Batches
ApplyChanges hands the plane a whole batch of upserts and deletes in one pass, as one commit group. The evidence page shows how the cost of a batch grows with its size, and that one insert followed by a group-by costs about the same at 100,000 rows as at 1,000,000.
What it costs
On a 1,000,000-row table the plane is slower than the engine alone on whole-table COUNT, whole-table SUM, single-column GROUP BY and MIN and MAX, because the engine reads a maintained total in microseconds there. It adds to single-row INSERT and UPDATE, and to bulk load a little. Every cost is in the evidence record beside the wins.
Automatic by default
With no declaration at all, the engine watches which aggregate statements keep scanning, and when the scanning has cost as much as a summary would cost to build it builds that summary itself (inline for tables up to a million rows, in the background above that while writes continue), names it auto_<table>_summary, and drops it again if the workload moves on. SET summaries = auto | declared | off and SHOW SUMMARIES control and show it, and EXPLAIN says which summary answered and why it was built. The answers are the same with or without it.
On paged tables too
The same rule builds the summary in the background from a paged table's pages, keeps it exact through appends, updates, deletes and transactions, and saves it beside the table, checksummed and valid only for the state it was saved from. A fresh paged table scans its first calls; after three repeats and enough scan time to pay for the build, the same statements are answered from the summary.
A sorted index for the big scan
A paged table can keep a sorted index on an INT column (16 bytes per row, read from disk in checksummed blocks). A range count, MIN and MAX, and the 20 largest are answered from the index whatever the table size: at 30,000,000 rows, warm, 0.002 ms against 2.7 ms for the scan. It stays exact through appends, updates and deletes, is saved with the data, and the planner builds one by itself when the scans have paid for it.
A keyed summary for the high-cardinality joins
For every customer id the exact count and sum, so top customers and revenue by segment are answered from the 600,000 keys instead of the 30,000,000 rows (12 ms and 13 to 30 ms cold after a restore; the scans took 120 to 1,170 ms). Joins with a dimension are kept as exact pre-grouped totals that every appended row and every new customer updates as it arrives, and a customer who changes segment moves their totals. At 100,000,000 invoices the four dimension joins answer in 0.19 to 0.25 ms warm and top customers in 0.58 ms warm (medians of three, one run, structures declared and loaded from their saved files). The planner builds the summary when the scans have paid for it, counting the writes the table has seen: a table that is mostly written to does not get one. The comparison with tuned DuckDB and tuned SQL Server is on the evidence page, with the queries HoloDb loses.
Restored from a backup, nothing to rebuild
Declare the summary on a paged table (CREATE INDEX ... USING SUMMARY) and it is saved beside the data with the table's group indexes and sorted key, each checksummed and trusted only for the exact table state it was saved from. A database restored from a backup opens with all of it present, and the first query is answered from the summary with no pass over the data. A stale or damaged file is discarded or rebuilt from its saved definition, and SHOW SUMMARIES says why.
Limits
A plane attached with EnablePleroma is for memory-resident tables and is not persisted, so call it again after Open. A plane created with SQL, or built automatically, is logged and saved with the snapshot, so Open does not rebuild it, and it survives Checkpoint. On a paged table CREATE INDEX takes USING SUMMARY, SORTED or KEYED, and the planner builds the same structures by itself. A plane serves a dimension only up to its cap of distinct values and a join of at most 4,095 keys, and declines anything else to the engine.

Index SQL and EXPLAIN: build it and see why

The plane has a SQL form, so a remote client can build it through the server like any statement. SHOW INDEXES reports its size and how many queries it served and declined, and EXPLAIN reports why a query was served or declined, without running it.

EXPLAIN runs the engine's own routing code in a mode that stops before the heavy work, so what it reports is the decision the real statement takes. It does not run an IN (SELECT ...) subquery, which it shows unresolved. A binary older than the release that added this SQL cannot open a log or snapshot that contains it.

C#
using HoloDb;

var db = Database.Open();
db.Execute("CREATE TABLE sales (id INT PRIMARY KEY, region TEXT, tier INT, qty INT)");
db.Execute("INSERT INTO sales (id, region, tier, qty) VALUES (1,'north',1,10),(2,'north',2,-4),(3,'south',1,7),(4,'east',3,5),(5,'south',2,9)");

// build the plane from SQL: key columns are dimensions, INCLUDE columns are measures
db.Execute("CREATE INDEX by_region ON sales (region, tier) INCLUDE (qty) USING SUMMARY");
db.PleromaMode = PleromaMode.Always;

Console.WriteLine(db.Execute("SELECT SUM(qty) FROM sales WHERE region = 'north' OR tier = 3").Rows[0]["sum(qty)"]);

// why was it served, or declined?
foreach (var r in db.Execute("EXPLAIN SELECT region, SUM(qty) FROM sales WHERE region = 'north' GROUP BY region").Rows)
    Console.WriteLine($"{r["kind"]}: {r["route"]}");
foreach (var r in db.Execute("EXPLAIN SELECT COUNT(*) FROM sales WHERE qty > 5").Rows)
    Console.WriteLine($"{r["kind"]}: {r["route"]}");

Console.WriteLine(db.PleromaVerify("sales") ?? "plane equals a rebuild from the columns");
Console.WriteLine(db.PleromaSumExact("SELECT SUM(qty) FROM sales"));

The Pleroma page store: durable, checksummed pages

PleromaPageStore holds many exact Pleroma pages as the data itself, durably and larger than memory, with no columns behind them. PleromaSparsePageStore does the same for sparse pages over a large vocabulary.

Checksummed pages
Every page carries a check prime, a mirror of its cells in a second prime, and a header hash. Verify proves every record and parity group intact. VerifyOnLoad does the same on every load and is off by default (about 100 microseconds for a 110-key page).
Parity repair
Records are grouped (8 by default) with one exact-sum parity record per group, and the members of a group sit on different 8 KB pager pages. Any one lost pager page, or any one damaged record per group, is rebuilt by Repair. A rebuilt page must pass its own check before it is written, and a page whose group parity is also damaged is reported as unrecoverable, never rebuilt wrong.
Restore points
Checkpoint returns a restore point, and RestoreTo returns the store to exactly that state with no recount. It is copy-on-write, so a restore point costs one before-image per page changed since, not a copy of the data. Eight are kept by default.
Exactly-once replay
Every AddBatch is journaled (fsynced by default) before it is applied, and each page remembers the last batch applied to it, so crash recovery applies a logged add exactly once, even over pages already flushed. A torn journal tail is discarded, so a batch survives whole or not at all.

Limits: one shape per store, and it must be CompleteKeys and admissible for a check prime. Shapes with a continuous component or a relation face cannot be saved. One process opens a store at a time and one writer works at a time. A batch is applied page by page, so a reader sees every page whole but may see a batch on some pages and not on others. The sparse store has no parity groups, restore points or event journal. Page-store throughput is not reported.

C#
using HoloDb;
using Phasor;

var shape = new HologramShape { KeyCapacity = 2, KeyCycle = 110, CompleteKeys = true };
var dir = Path.Combine(Path.GetTempPath(), "plrstore-restore");
if (Directory.Exists(dir)) Directory.Delete(dir, true);

using (var store = PleromaPageStore.Open(dir, shape))
{
    store.AddBatch(new[] { new PageAdd(42, 5, 3) });
    var point = store.Checkpoint();                       // a restore point: id and journal position
    store.AddBatch(new[] { new PageAdd(42, 5, 10), new PageAdd(9, 1, 1) });
    Console.WriteLine($"{store.Counts(42)[5]} {store.Contains(9)}");

    store.RestoreTo(point.Id);                            // back to the point, no recount
    Console.WriteLine($"{store.Counts(42)[5]} {store.Contains(9)}");

    Console.WriteLine(store.Verify().Clean);
    Console.WriteLine(store.Repair().Unrecoverable.Count);
}
Directory.Delete(dir, true);

Exactness

The plane returns row-for-row the same answers as the engine and SQLite across its parity suite, including a random insert, update, delete, rollback and reopen log, and sums past 64 bits, and the page store passes its fault suite. The checks, and the deliberate mutations that turned them red, are listed with the figures.
