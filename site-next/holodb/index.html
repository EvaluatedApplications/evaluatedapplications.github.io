See the numbers

  • Learned records under writes

    After a stream of single-row UPDATEs and DELETEs over six learned scatter predicates on 1,000,000 rows, the next sweep reads 6 blocks with records that adjust, against 60 and 51 blocks when updates drop them. After consolidation it reads 6 blocks against 366. All counts, sums and zones were verified exact against the cells in every phase.

  • Upkeep priced from measured cost

    On a mixed stream of 1,200 delete-or-update pairs each followed by a sorted count, the index with measured upkeep stayed built and read 0 blocks, using 49,306 to 54,106 page pins in all, against 1,158,839 pins when the structure was dropped at the 256th write and rebuilt by scans.

  • Crash recovery against SQLite

    Across 8 archived customer runs and 158 sessions the customer lifecycle test compared 249 million rows against SQLite, ran 8,267 SELECTs and 1,129 checked DML statements, and recovered 46 times after a kill or a cut: 37 times to the state before the interrupted write, 9 times to the state after, and none to a state between them.

  • Counts are exact

    Blocks, pins, runs and bytes are exact counts. A pin is one page read through the buffer pool, and counts of pins stand in for time.

What you can build

Each one is in the package today.

  • A store that tunes itself to its workload

    Repeat a question and the engine builds the structure that repeated queries have paid for, and drops it when the workload moves on or when a write would make it cost more than it saves. Nothing is declared and no index is designed.

  • Exact aggregates that read a maintained total

    One copy of the data answers a lookup by key in ordinary SQL, similarity search with NEAREST, and exact aggregates that read a maintained total instead of scanning. INT sums are 128-bit running totals.

  • Similarity search in one statement

    Rank rows by how closely they match a partial description with NEAREST, in the same SQL, with a score column on request.

    See NEAREST

  • A database that survives a power cut

    BEGIN, COMMIT and ROLLBACK run over a write-ahead log with group commit: a statement that has returned is on disk. A power cut leaves the table as it was before or as it is after, never between.

  • Look back with AS OF

    Read a paged table as it was after any commit the history still holds, and fingerprint it with Seal so replicas can compare.

    See AS OF and Seal

  • Tables bigger than memory

    Paged tables read through a buffer pool of 8 KB pages, with a logical block map and a CRC-32C checksum on every log block and data page.

  • Apply a batch of changes atomically

    ApplyChanges applies a batch of upserts and deletes as one step, and KeyDigest and Seal compare key sets and tables across replicas.

    See atomic batches and upsert

  • Real SQL NULL on paged tables

    Declare a column NULL and it holds true nulls with three-valued logic. A statement that names a nullable column reads only the columns it names.

C#
using HoloDb;

var db = new HoloDbService(new HoloDbOptions());
db.Execute("CREATE TABLE users (id INT PRIMARY KEY, age INT, name TEXT)");
db.Execute("INSERT INTO users VALUES (1, 30, 'Ada')");

var result = await db.ExecuteAsync("SELECT name FROM users WHERE age >= 18");
foreach (var row in result.Rows) Console.WriteLine(row["name"]);
// Ada
Output
Ada

A WalPath in the options makes the database durable. For a database whose tables can be larger than memory, set both WalPath and Paged = true. Paged = true without a WalPath throws.

Similarity search in one statement. NEAREST ranks the rows by how close they are to the description.

C#
using HoloDb;

var db = new HoloDbService(new HoloDbOptions());
db.Execute("CREATE TABLE products (id INT PRIMARY KEY, category TEXT, price INT)");
db.Execute("INSERT INTO products VALUES (1,'electronics',100),(2,'electronics',120),(3,'furniture',300)");

var near = db.Execute("SELECT id, category, price, score FROM products NEAREST (category = 'electronics', price = 118) LIMIT 2");
foreach (var row in near.Rows) Console.WriteLine($"id={row["id"]} category={row["category"]} price={row["price"]} score={row["score"]:F3}");
// id=2 category=electronics price=120 score=0.993
// id=1 category=electronics price=100 score=0.988

What it is, and how it learns

HoloDb is an embedded SQL database for .NET. You create tables and write SQL. Tables are typed columns, in memory or on disk. The answer to every SQL statement is exact. NEAREST ranks exactly on small tables and approximately above a size threshold. The engine watches the workload it serves and builds only the structures that repeated queries have paid for. It drops them when the workload moves on or when a write would make them cost more than they save.

One copy of the data answers three kinds of question: a lookup by key in ordinary SQL, similarity search with NEAREST, and exact aggregates that read a maintained total instead of scanning. Everything the engine builds is derived from the columns, so losing a derived structure costs time and never data.

Three terms recur on these pages. A block is a run of rows stored together. A page is 8 KB of file. A pin is one page read through the buffer pool, and counts of pins stand in for time.

  • Learned records that stay right when rows change

    For a filter you ask for often, the engine writes a card for each block of rows: how many rows match, and the exact sums of the columns you total. The next time you ask, it reads the cards and opens only a block whose card a write has touched. When an UPDATE or DELETE changes rows, or consolidation moves them, the cards are corrected by the exact difference. Each card carries its own checksum lanes and is checked when it is read and when the database opens, so a wrong card is dropped and relearned and never changes an answer.

  • A ski-rental ledger decides what to build and what to drop

    Renting skis is cheap for one weekend and buying wins after enough weekends. The engine keeps that ledger for every structure. Each scan that a structure would have saved is rent. The structure is built when the rent paid has reached the cost of building it, and dropped when the cost of keeping it up through writes exceeds what it saves. The cost of keeping a structure up is the time its delta path really takes on this machine, measured per write and averaged.

  • Gather, regroup and placement lay rows out by what reads waste

    If the rows a filter wants are scattered over the whole table, every repeat reads many blocks to find a few rows. The engine measures that waste, in time, for each learned filter. Gather moves matching rows next to each other when the time saved by repeats is larger than the cost of the move. Regroup rewrites the whole layout once, when gather alone cannot reach it. Placement puts a newly written row in a block the repeated filters already read. A repeat that the stored counts and sums already answer reads nothing, so it pays no rent and nothing is moved.

  • A paged store with a logical block map

    Every page has a logical number, and a map takes that number to a place in the file. The map changes only inside a committed log batch, so a moved or rewritten page never leaves the file half-changed, and a shrunk table keeps its freed pages and refills them. A page that fails its checksum is an error that names the page, never a changed answer.

  • ACID with crash-tested recovery

    The write-ahead log holds signed page deltas in a ring file whose size follows the largest recent batch, with group commit. A failed statement inside a transaction undoes only itself. A transaction larger than the buffer pool spills to a scratch file, and a rollback or a power cut leaves the table as it was. Each commit is kept as a signed record within a retention budget.

  • Real SQL NULL on paged tables

    Declare a column NULL and it holds true nulls with three-valued logic, on paged tables as well as in memory. COUNT(col), SUM, AVG, MIN and MAX skip nulls, GROUP BY makes one null group, and a join never matches one. Null counts are maintained. A point read of one row on a wide nullable table takes about 110 page pins at 100,000, 300,000 and 1,000,000 rows.

Everything in the package

  • SQL

    CREATE TABLE [IF NOT EXISTS], ALTER TABLE ... ADD COLUMN, CREATE INDEX (sorted, summary, keyed; automatic indexes need no declaration), DROP INDEX, SHOW INDEXES, SHOW SUMMARIES, SET summaries and SET indexes, EXPLAIN, INSERT (with ON CONFLICT ... DO UPDATE), UPDATE, DELETE, SELECT with DISTINCT, aggregates, COUNT(DISTINCT), INNER JOIN, WHERE (AND, OR, NOT, LIKE, IN, BETWEEN, IS NULL, IN (SELECT ...)), GROUP BY, HAVING, ORDER BY, LIMIT, NEAREST, and BEGIN, COMMIT, ROLLBACK.

  • Exact

    INT sums are 128-bit running totals and throw only past 64 bits. Empty selections give NULL for SUM, AVG, MIN and MAX, and 0 for COUNT.

  • Learns by use

    Summaries, sorted and keyed indexes, a tree of exact sums, learned block records with exact partial sums, learned routes, zones that skip blocks, top-k by zones, gather and placement. One budget covers them all and is a hard cap. EXPLAIN says which structure answered a statement, or why none did.

  • Look back

    AS OF n and Seal(table, asOf: n) on paged tables.

  • Analytic SQL

    Narrow column types, dictionary-coded text, CASE, CAST, EXTRACT, DATE_TRUNC, REGEXP_REPLACE, positional GROUP BY and ORDER BY, and COUNT(DISTINCT) on large cardinalities.

  • Change feeds

    ApplyChanges applies a batch of upserts and deletes atomically. KeyDigest compares two key sets in modulus numbers. Seal fingerprints a table so shards add and replicas compare.

  • Aggregate plane (optional)

    An exact derived summary of small-domain columns, served through Phasor's Pleroma stores, with PleromaVerify to check it against the columns.

  • Metering

    MeteredDatabase reports the rows and bytes each query read.

  • Integration

    services.AddHoloDb() for dependency injection, and an EvalApp context for pipelines.

Know before you start

What HoloDb does not do, and where to be careful
  • Scale: the correctness suites run to 3,000,000 rows in both pipeline modes. Larger tables work, but the lifecycle and crash guarantees are tested at 3,000,000.
  • Writers: one. Reads run in parallel and lock-free for simple selects; writes, DDL and transactions take one lock at a time.
  • Joins: INNER JOIN only. A paged table takes one join per statement; in-memory tables take several. A join on a paged table with NULL columns is refused by name.
  • SQL not offered: UNION, window functions, subqueries other than IN (SELECT ...), table aliases, DROP COLUMN and column rename. UPDATE ... SET takes a literal on its right side.
  • NEAREST: does not combine with GROUP BY or with a join on a nullable table. It ranks exactly on small tables and approximately above a size threshold.
  • Keys and types: one primary key per table, INT or TEXT. Types are INT, TEXT and REAL, with narrow integer, date, timestamp and fixed-width text types on analytic tables.
  • In-memory only: ApplyChanges and the upsert form run on in-memory tables. A paged table refuses them.
  • Row order: without ORDER BY, the order of rows is unspecified and can change after a DELETE or a write that moves a row.
  • Structures: they help repeated work. A filter whose matching rows are spread evenly over every block gains nothing from learned records. The first lookup of a value no earlier read has seen is a scan, except a text value absent from the column or a number outside its range, which read no block. Moving scattered rows costs about 200 microseconds per row, so a scattered filter pays that back after about 100 uses.
  • Older data: paged tables written by older formats, older write-ahead logs, and a text-format database opened as paged all throw a named error that says to export the rows and load them into a new database. There is no in-place upgrade.
  • History: AS OF works on paged tables and reads sequences the history still holds. A sequence below the floor, inside a retained segment, or on an in-memory table is refused by name, as is a join under it.
