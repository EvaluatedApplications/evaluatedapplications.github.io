How it gets there

Six short scenes. The motion is schematic; the numbers are measured.

The engine learns what you read

Ask the same question twice and the second time reads almost nothing, even after writes.

Rent or buy

The engine pays for a structure or a move only when the rent has reached the price.

Crash and come back

Cut the power in the middle of a commit. The table that opens is the table before or the table after.

When HoloDb fits, and when it does not

Everything is a trade-off. Set your workload and read the answer, including when to use something else.

The five trade-offs

  • Read speed against write cost

    Reads

    A total over 100,000,000 invoices reads in 0.12 ms, because totals are kept up to date as rows are written.

    Writes and space

    Single-row INSERT, UPDATE and DELETE took 1.5 to 2.1 times SQLite's time (engine alone, in memory). The structures take space: 6.84 GB restored, 4.94 GB out of the box, 2.46 GB for tuned DuckDB.

  • Exact against approximate

    Exact

    Integer sums are 128-bit and identical on all four engines for all 16 queries. A sum past 64 bits throws; it never wraps.

    Approximate

    Only similarity search: from 8,000 rows an approximate index picks the candidates. Money is integer cents, because DECIMAL is a double.

  • Automatic against hand-tuned

    Automatic

    The planner builds a summary or index when repeats pay for it, and drops it when writes cost more than it saves.

    Hand-tuned

    A DBA can declare structures, which are saved and never dropped. Without them, scans no structure covers are slower than tuned DuckDB: 5 of 16 queries at 100,000,000 invoices.

  • Embedded against server

    Embedded

    In process: a point query takes 1 to 3 microseconds. One process owns the files and one writer runs at a time.

    Server

    TCP and TLS with a typed .NET client: about 0.07 ms more per point query. No JDBC, ODBC or PostgreSQL wire.

  • Memory against disk

    In memory

    The fastest path, bounded by RAM at about 110 bytes per row.

    Paged

    Tables bigger than memory through an 8 KB buffer pool: 100,000,000 invoices in 4.94 GB, 165 s to load, a 3.16 GB peak working set out of the box and 1.26 GB restored.

What you can build

Each one is in the package today.

  • Live dashboards with no cache layer

    Totals, counts, minimums, maximums and single-column group-bys over integer columns read a maintained value, so the answer stays flat from a thousand rows to tens of millions.

  • Search by resemblance, in SQL

    Rank rows by how closely they match a partial description, over the rows the table already holds. A close number or date, or a near-identical string, ranks ahead of a far one, with no separate vector index.

  • A database that survives a crash

    Write-ahead logging with an fsync on each durable commit, and recovery bounded by your live data, not by how much you have ever written.

  • Apply a thousand changes as one atomic step

    Feed an ordered stream of upserts and deletes to one call and readers never see half a batch: they see the table before it or after it. The batch is one write-ahead-log commit group, and the same upsert is a line of SQL with ON CONFLICT.

    See atomic batches and upsert

  • Tables bigger than memory

    Paged tables spill cold pages to disk through an 8 KB buffer pool and keep the maintained totals accurate there.

  • One database, in process or over the network

    Use it inside your app, or run it as a server with a typed client and a columnar wire protocol. The same managed code also runs in a browser tab, which is how The Analyst works.

  • Exact answers from a small summary

    Attach an optional plane to chosen columns and filters, group-bys and joins are answered without scanning the table.

    See HoloDb on the Pleroma

One store, three ways to ask

HoloDb is an embeddable SQL database for .NET with ACID transactions, similarity search and maintained aggregates. Rows live in typed columns, and everything else is derived from them: a holographic vector built from a row's columns powers similarity search by content, exact integer accumulators answer aggregates without a scan, and exact derived summaries answer filters and group-bys. So the same copy of the data is read three ways. Exact lookup by primary key is ordinary SQL. Similarity search by content is the NEAREST clause. Analytics read a maintained total instead of scanning.

Applications that need relational storage, similarity search and fast dashboard rollups normally reach for three systems, a row store, a vector index and a cube or a pile of scans, and pay to keep them consistent. HoloDb is one embeddable package: a transactional store, an in-SQL similarity search, and aggregates whose response time does not grow with the table.

  • No separate vector index

    NEAREST ranks rows by resemblance to a partial description, in SQL, over the rows the table already holds. A close number or date, or a near-identical string, ranks ahead of a far or unrelated one, and the score is readable as a column.

  • Aggregates do not scan

    An integer column's running total is a maintained exact accumulator, so whole-table COUNT, SUM, MIN and MAX and single-column GROUP BY read that value directly, flat as the table grows from a thousand rows to tens of millions. An INT SUM never wraps: it is held in 128 bits, and the statement throws only if the true total leaves 64 bits.

  • Real ACID, and past RAM

    Write-ahead logging with an fsync on each durable commit, crash recovery bounded by live data and not by write history, reader and writer locking, and paged tables on an 8 KB buffer pool that let a table exceed memory.

  • Damage is reported, never read as an answer

    The columns are the source of truth, and every hologram, summary and index is derived from them. A paged table checks every data page, so a page that fails its checksum is refused with an error that names the page. In a test that flipped 61 bits in the data file of a 91 MB paged table, none gave a silently different answer: 36 were reported and 25 were in pages never read.

Everything in the package

  • A substantial SQL dialect

    CREATE TABLE, INSERT, UPDATE, DELETE, SELECT with DISTINCT, COUNT, SUM, MIN, MAX and AVG, INNER JOIN (several in one statement on in-memory tables, one on a paged table), WHERE with AND, OR, NOT, LIKE, IN, BETWEEN, IS NULL and IN (SELECT ...), GROUP BY and HAVING, ORDER BY, LIMIT, ALTER TABLE ADD COLUMN, indexes, EXPLAIN, and explicit BEGIN, COMMIT and ROLLBACK.

  • Real SQL NULL

    Declare a column NULL and it holds true NULLs with three-valued logic: COUNT(col), SUM, AVG, MIN and MAX skip them, GROUP BY makes one NULL group, ORDER BY puts them first, and a join never matches one. Whole-table aggregates and one-column group-bys stay maintained answers with NULLs present: 0 rows read at 10,000 to 640,000 rows with half the values NULL. On an empty selection SUM, AVG, MIN and MAX are NULL and COUNT is 0, for a NOT NULL column as well.

  • Parameterized queries

    Every Execute has a ? placeholder overload with positional binding, correctly quoted and escaped, beside the raw SQL string form.

  • Content similarity in SQL

    NEAREST ranks by graded closeness for numbers, dates and text, with a score column on request. From 8,000 rows an approximate sublinear index ranks candidates, and below that or whenever the query has a WHERE the ranking is an exact scan.

  • Constant-time exact aggregates

    COUNT, SUM, MIN, MAX and single-column GROUP BY over integer columns are exact, not approximate. Real-number aggregates use a fast SIMD scan.

  • Durable and larger than memory

    A snapshot plus a short log gives recovery that tracks live data. Paged tables spill cold pages to disk and keep the maintained aggregates accurate there. Every 8 KB data page carries a checksum, UPDATE and DELETE move only the pages that change, and a statement may change more pages than the buffer pool holds: a rollback or a power cut still leaves the table as it was.

  • Summaries and indexes that build themselves

    With nothing declared, the engine watches which aggregate statements keep scanning and, when the scanning has cost as much as a summary would cost to build, builds it, in memory or on a paged table, and drops it again if the workload moves on. A predicate that matches a small fraction of a large table earns a sorted or an equality index the same way. EXPLAIN says what answered a query and why. SET summaries and SET indexes switch this between auto, declared and off, and the answers are the same either way.

  • A table with no rows

    CREATE SUMMARY TABLE makes a table that keeps only the exact plane and the position each feed has reached, so memory does not depend on how many rows passed through it. COUNT, SUM, AVG, GROUP BY, HAVING and a WHERE over the dimensions still answer exactly, and a replayed feed never counts twice. Anything that needs a row is refused with the reason.

  • Atomic change batches and upsert

    ApplyChanges applies a whole batch of upserts and deletes under one write lock, as one write-ahead-log commit group, so a reader sees the table before the batch or after it and never part of it. INSERT with ON CONFLICT (key) DO UPDATE SET is the SQL upsert. Both work on in-memory tables.

  • Fast scans

    A WHERE is evaluated over raw column arrays in tight loops, GROUP BY over INT and TEXT columns uses dense codes, and an equi-join on TEXT keys is a columnar hash join.

  • Metering

    A per-query usage meter reports the rows and bytes actually processed, for billing or observability.

  • Embedded or networked

    Use it in process, or run it as a server with a matching typed client and a columnar wire protocol. The same managed code also runs in a browser tab.

  • The optional Pleroma plane and page store

    Attach an exact, derived summary to chosen columns to answer filters, group-bys, distinct counts and joins without scanning, or keep exact Pleroma pages durably as the data itself.

Know before you start

What HoloDb does not do, and where to be careful
  • Joins: INNER JOIN only. Several in one statement on in-memory tables, one on a paged table. LEFT, RIGHT, FULL, CROSS, NATURAL, USING and comma joins are refused.
  • Aliases: No AS on columns or tables. Aggregate columns are named agg(col), such as count(*).
  • ALTER TABLE: ADD COLUMN only, with a DEFAULT or NULL. No DROP COLUMN, RENAME COLUMN or RENAME TO.
  • Expressions: No CASE, LENGTH(), OFFSET or UNION, and no arithmetic in the select list or inside SUM(v * 2). COUNT(DISTINCT col), LIKE and IN (SELECT ...) work on in-memory tables.
  • Money: Constant-time totals are for INT columns. REAL SUM is a SIMD scan, and DECIMAL and NUMERIC are REAL (a double), so hold money as integer cents. There is no fixed-point type.
  • Saved summaries: A summary made with CREATE INDEX ... USING SUMMARY, or built by the planner, is saved with the table and restored on open. A plane attached with the EnablePleroma call on an in-memory table is not saved: call it again after Open.
  • Summary limits: A declared summary takes up to 4,095 distinct values per column (1,024 for one the planner builds) and a joint of 12 bits. A column over its limit goes to a scan and is never approximated.
  • Joins on paged tables: The keyed summary holds up to 4,194,304 consecutive INT keys. The 100,000,000-invoice run joins 2,000,000 customers.
  • Languages: A .NET library. The server speaks a TCP and TLS binary protocol whose only client is .NET. No JDBC, ODBC, Python, Node or Go client, and no PostgreSQL or MySQL wire.
  • Concurrency: One process per database and one writer at a time. Simple aggregate reads run off a snapshot without the lock. A second process cannot open a paged database's files, and there is no MVCC: a long transaction blocks other writers.
  • Table size: Tested to 100,000,000 rows (4.94 GB paged, 165 s to load). In-memory tables are bounded by RAM at about 110 bytes per row. A paged primary key loaded out of order keeps a RAM dictionary of about 35 bytes per row. Beyond 100,000,000 rows is untested.
  • Backup: Offline: copy the files of a closed database. There is no online backup and no point-in-time recovery.
  • Crash safety: One fsync per commit. Tests cut the log at every record boundary, flip bits in the log and the data file, and tear a page during a checkpoint. A real power cut, a disk that lies about fsync, a full disk and several processes are not tested.
  • Upsert: a plain INSERT of an existing primary key throws. To insert or replace, use INSERT with ON CONFLICT (key) DO UPDATE SET column = EXCLUDED.column, or ApplyChanges with RowChange.Upsert. Both work on in-memory tables only, and a paged table refuses them.
  • Keys: a table has one PRIMARY KEY, an INT or TEXT column.
  • NULL: a column holds NULL only when it is declared NULL. An index takes NOT NULL columns only, paged tables and summary tables refuse NULL, and the Pleroma plane hands any statement that touches a column holding a NULL to the engine. A statement on a column holding NULLs that is not a maintained aggregate reads boxed rows, slower than a NOT NULL column. A table that declares a NULL column is not read lock-free.
  • Similarity: NEAREST with a WHERE filters first and then ranks the survivors, and NEAREST does not combine with GROUP BY.
  • Documentation: the package ships compiled, without XML documentation.

Every public type is documented with a worked example in the package readme on NuGet. Open the NuGet page.
