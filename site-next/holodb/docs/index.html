Install and first query

Add the package from NuGet with dotnet add package EvaluatedApplications.HoloDb. You create tables and write SQL. Tables are typed columns, in memory or on disk.

A WalPath in the options makes the database durable. For a database whose tables can be larger than memory, set both WalPath and Paged = true. Paged = true without a WalPath throws.

C#
using HoloDb;

var db = new HoloDbService(new HoloDbOptions());
db.Execute("CREATE TABLE users (id INT PRIMARY KEY, age INT, name TEXT)");
db.Execute("INSERT INTO users VALUES (1, 30, 'Ada')");

var result = await db.ExecuteAsync("SELECT name FROM users WHERE age >= 18");
foreach (var row in result.Rows) Console.WriteLine(row["name"]);
// Ada
Output
Ada

The SQL dialect

The answer to every SQL statement is exact. Types are INT, TEXT and REAL, with narrow integer, date, timestamp and fixed-width text types on analytic tables. A table has one primary key, INT or TEXT.

Statements
CREATE TABLE [IF NOT EXISTS], ALTER TABLE ... ADD COLUMN, CREATE INDEX, DROP INDEX, SHOW INDEXES, SHOW SUMMARIES, SET summaries, SET indexes, EXPLAIN, INSERT (with ON CONFLICT ... DO UPDATE), UPDATE, DELETE, SELECT, and BEGIN, COMMIT and ROLLBACK.
SELECT
DISTINCT, aggregates, COUNT(DISTINCT), INNER JOIN, WHERE with AND, OR, NOT, LIKE, IN, BETWEEN, IS NULL and IN (SELECT ...), GROUP BY, HAVING, ORDER BY, LIMIT and NEAREST.
Joins
INNER JOIN only. A paged table takes one join per statement; in-memory tables take several. A join on a paged table with NULL columns is refused by name.
Exact sums
INT sums are 128-bit running totals and throw only past 64 bits. Empty selections give NULL for SUM, AVG, MIN and MAX, and 0 for COUNT.
Analytic SQL
Narrow column types, dictionary-coded text, CASE, CAST, EXTRACT, DATE_TRUNC, REGEXP_REPLACE, positional GROUP BY and ORDER BY, and COUNT(DISTINCT) on large cardinalities.
Not offered
UNION, window functions, subqueries other than IN (SELECT ...), table aliases, DROP COLUMN and column rename. UPDATE ... SET takes a literal on its right side.
Row order
Without ORDER BY, the order of rows is unspecified and can change after a DELETE or a write that moves a row.

Structures that build themselves

The engine watches the workload it serves and builds only the structures that repeated queries have paid for: summaries, sorted and keyed indexes, a tree of exact sums, learned block records with exact partial sums, learned routes, zones that skip blocks, top-k by zones, gather and placement. It drops them when the workload moves on or when a write would make them cost more than they save. One budget covers them all and is a hard cap.

SET indexes and SET summaries choose whether automatic indexes and summaries are built (auto), only declared ones are kept (declared), or none answers a query (off). EXPLAIN says which structure answered a statement, or why none did. The answers are the same in every setting.

How the engine learns

NULL

Declare a column NULL and it holds true nulls with three-valued logic, on paged tables as well as in memory. A statement that names a nullable column takes an exact path that reads only the columns it names.

COUNT(col), SUM, AVG, MIN and MAX skip nulls, GROUP BY makes one null group, and a join never matches one. Null counts are maintained. A point read of one row on a wide nullable table takes about 110 page pins at 100,000, 300,000 and 1,000,000 rows.

Similarity search

NEAREST ranks rows by how closely they match a partial description, with no separate index. It ranks exactly on small tables and approximately above a size threshold. It does not combine with GROUP BY or with a join on a nullable table.

C#
using HoloDb;

var db = new HoloDbService(new HoloDbOptions());
db.Execute("CREATE TABLE products (id INT PRIMARY KEY, category TEXT, price INT)");
db.Execute("INSERT INTO products VALUES (1,'electronics',100),(2,'electronics',120),(3,'furniture',300)");

var near = db.Execute("SELECT id, category, price, score FROM products NEAREST (category = 'electronics', price = 118) LIMIT 2");
foreach (var row in near.Rows) Console.WriteLine($"id={row["id"]} category={row["category"]} price={row["price"]} score={row["score"]:F3}");
// id=2 category=electronics price=120 score=0.993
// id=1 category=electronics price=100 score=0.988
Output
id=2 category=electronics price=120 score=0.993
id=1 category=electronics price=100 score=0.988

Transactions and durability

BEGIN, COMMIT and ROLLBACK run over a write-ahead log of signed page deltas in a ring file whose size follows the largest recent batch, with group commit: a statement that has returned is on disk. A failed statement inside a transaction undoes only itself.

A transaction larger than the buffer pool spills to a scratch file, and a rollback or a power cut leaves the table as it was. The tests cut the power inside COMMIT and kill the process, and the table that opens is the table before or the table after.

What we test

AS OF and Seal

Each commit is kept as a signed record within a retention budget, so SELECT ... FROM t AS OF n reads a paged table as it was after commit n for any n the history still holds. Seal(table, asOf: n) gives an order-free fingerprint that replicas can compare.

AS OF works on paged tables. A sequence below the floor, inside a retained segment, or on an in-memory table is refused by name, as is a join under it.

Atomic change batches and upsert

ApplyChanges applies a batch of upserts and deletes atomically. KeyDigest compares two key sets in modulus numbers. Seal fingerprints a table so shards add and replicas compare.

INSERT with ON CONFLICT ... DO UPDATE is the SQL upsert. ApplyChanges and the upsert form run on in-memory tables, and a paged table refuses them.

Tables larger than memory

Paged tables read through a buffer pool of 8 KB pages. Every page has a logical number, and a map takes that number to a place in the file. The map changes only inside a committed log batch, so a moved or rewritten page never leaves the file half-changed, and a shrunk table keeps its freed pages and refills them.

Every log block and every data page carries a CRC-32C checksum. A page that fails its checksum is an error that names the page, never a changed answer. Paged tables written by older formats, older write-ahead logs, and a text-format database opened as paged all throw a named error that says to export the rows and load them into a new database. There is no in-place upgrade.

The aggregate plane

The plane is optional. It is an exact derived summary of small-domain columns, served through Phasor's Pleroma stores, with PleromaVerify to check it against the columns.

Metering and integration

MeteredDatabase reports the rows and bytes each query read.

services.AddHoloDb() registers HoloDb for dependency injection, and an EvalApp context runs it inside pipelines.

Over the network

The same engine runs as a server, and a typed client talks to it over TLS with the same surface as the in-process engine.
