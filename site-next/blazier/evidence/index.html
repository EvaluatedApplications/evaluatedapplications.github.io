Blazier evidence

What a visitor waits for

On the sample app the static page downloads 6.8 KB before the visitor acts, against 2.8 MB when the same app boots the usual way. Real content is on screen in 72 to 100 ms on desktop and 416 to 484 ms on the phone profile, against 748 to 1,165 ms and 13.2 to 15.5 s. After the visitor presses Start the runtime takes 710 to 1,170 ms on desktop and 12.7 to 15.4 s on the phone profile to reach a working page, the same wait as the usual boot.

Where it is slower

Every loss in this record, stated once
  • Pressing Start does not shorten the wait for the runtime: a working page takes 12.7 to 15.4 s after the press on the phone profile, against 13.2 to 15.5 s for the usual boot. Blazier moves the wait behind a readable page and does not remove it.

How it was measured

Stated once, for every figure on this page
Workload
The Blazier sample app, the sample app published with the trimmed interpreter build, is loaded in headless Microsoft Edge from a local server shaped like GitHub Pages, with gzip. The same page is loaded two ways: booted the usual way, and as a Blazier static shell that starts the runtime when the visitor presses Start. The worker rows run a prime count to 600,000 in a worker service.
Engines
Blazier static shell; Blazor WebAssembly booted the usual way
Check
On a page with a click target, a touch scroll, a tap on text and a Tab key press make 0 requests for the runtime, while the control page starts it.
Statistic
Desktop is unthrottled, 3 runs. The phone profile is 4 Mbit/s, 100 ms round trip, CPU slowed 6 times, 2 runs. A range runs from the fastest to the slowest run.
Machine
An Intel Core i9-11950H laptop with 32 GB of memory.

Limits

  • One sample app on one machine. The figures describe that app, not a forecast for another.
  • The sample app uses the trimmed interpreter build. In an ahead-of-time build the lazy-assembly saving is small, because that native code lives in the main runtime file either way.
  • The worker rows are desktop only. The phone profile slows the page and not the worker, so a phone worker figure would describe the page. A worker runtime starts at about 32 MiB of memory.
  • Headless Edge only. Firefox and Safari have not been run, and the memory and battery cost on a phone are not measured.
  • The worker bridge was measured with a shared bundle. A separate worker bundle has been built but not run in a browser.
  • The Showroom tool pages are built this way, but their shell sizes and timings are not part of this record.
